# Cairn 1.0 completion plan (2026-11-08)

Status: **release-ready engineering; awaiting owner decisions.** Cairn is declared **1.0
(2026-11-07)** in `support.md`; **no 1.0 release tag has been cut** (latest published tag is
`v2026.09.13`). All P0 engineering gates are closed and `main` is green; the remaining P0 is the
human tag/publication, plus the security and policy decisions in section 8. This document records
what is proven, the final reliability fixes, and the few P1 evidence items that remain.

## 1. What is proven today

- **Durability.** The metadata transaction is the ACK point; object files and sidecars are the
  durable authority; protocol 3 rebuilds the index from object files at startup. The 24-hour soak
  completed 1,697,128 PUTs with 0 errors, 0 replication mismatches and 137,552 verified reads; the
  fixed 2-hour run held anonymous RSS at 155.6 → 153.5 MiB (−1.3%). The post-v44 2-hour gate
  **passed** with 137,831 PUTs, 0 errors/mismatches and anonymous RSS 162.4 → 154.1 MiB (−5.2%).
  The post-v44 **24-hour** gate also **passed**: 1,734,228 PUTs, 0 errors, 0 replication
  mismatches, 137,487 byte-verified reads and anonymous RSS 1,368.2 → 1,357.3 MiB (−0.8%;
  total RSS +4.1%, file-backed cache only).
- **Crash/recovery.** CI runs the F-4 crash consistency and the multi-point blob-commit crash
  harness, backup/restore/offline recovery, scrub, Object Lock/WORM, chunked/adversarial limits,
  replication soak/chaos and a mixed-feature leak soak. R-6/R-7/R-8 closed the thread-shape,
  WAL-growth and unwritable-log failures found by that soak; the thread gate is now a plateau test
  and WAL writes have a hard 256 MiB backpressure gate.
- **Security baseline.** No open GitHub code-scanning, Dependabot or secret-scanning alerts at the
  2026-09-25 closure; `cargo audit` and both npm audit policies are in CI; the audit register has no
  unresolved exploitable finding. Known accepted limits are the authentication-path rate limit
  (deploy behind a proxy), OpenRC units, and a residual risk limited to replication ciphertext
  written by pre-fix binaries.
- **Performance.** Against **RustFS 1.0.4**, every paired row is at or above parity: PUT 4 KiB
  1.73x, PUT 1 MiB 1.07x (parity), GET 4 KiB 1.15x, GET 1 MiB 1.64x, HEAD 1.18x, LIST 5.13x,
  Mixed 2.04x, multipart part GET 2.71x, multipart upload 1.08x (parity), bulk unversioned DELETE
  19.95x, single-key unversioned DELETE 16.53x, and versioned DELETE **32.49x** (equal durability).
  RustFS 1.0.2+ journals deletes under strict mode; the 1.0.0 delete rows are historical. The
  delete code path also improved 839.8 -> **1,447.3 obj/s (+72.3%)** in this campaign (2,400+ on the
  quieter 1.0.4 session) and LIST improved to **171,764 obj/s**; with the device flush cost removed
  it reaches **5,680 obj/s** (tmpfs diagnostic).

## 2. What "fully complete" means

A 1.0 is complete when all of the following hold on the release commit:

1. `main` is green on the full gate and on every release-blocking CI job.
2. A release tag and artifacts exist, produced by the release workflow with provenance and signed
   checksums, and the installer verifies them.
3. The supported upgrade path (`v2026.09.13` → current schema) is exercised in CI, including the
   v43/v44 rebuild, Object Lock/retention preservation, snapshot rollback and an old-binary refusal.
4. The release notes state migration time/space and the rollback procedure for the table rebuild.
5. The published scoreboard names the comparator version and pairs only comparable rows.
6. No open high/medium security finding; accepted limits are stated in `support.md`.
7. The 1.0 support statement, `Cargo.toml`/version identity, upgrade guide and README agree.

| # | Item | Acceptance |
|---|---|---|
| R-1 | **v44 startup rebuild** | **Done:** `backup_restore.sh` proves a row-loss rebuild restores ordinary/multipart rows, BLAKE3 and `?partNumber` (layout-less v1 fails closed); the upgrade drill proves the clustered shape and lock rows survive migration; and the new locked-object fixture proves a file-loss rebuild restores exact GOVERNANCE retention and legal hold from the sidecar. | Done |
| R-2 | **Backup/restore v44** | **Done:** the CI backup/restore e2e runs a v44 store through snapshot/restore with BLAKE3 and `?partNumber`, and the upgrade drill asserts exact Object Lock retention/legal-hold rows across the v44 rebuild and snapshot rollback. |
| R-3 | **Migration observability** | **Done:** every applied migration logs its version, name and elapsed seconds; startup logs the database size and unprivileged free bytes before migrations and the elapsed time plus WAL size after them, with a warning below the documented 3× space rule. This turns a long table rebuild into an observable startup event without adding a new metric-cardinality surface. |
| R-4 | **libSQL scope** | **Done:** `docs/metadata.md` and `docs/upgrade-rollback.md` state that SQLite is clustered at v44 while libSQL/Turso remain at v42 with the rowid layout, and that switching backends on a populated store is unsupported. |
| R-5 | **Operational drills** | **Partially proven:** the upgrade/rollback drill, backup/restore and disaster-recovery paths run in CI, and the 1M-row v44 migration measured 66 s/661 MB WAL. A production-shaped 100M-row drill still needs a real data copy and an operator window; it is deployment-specific, not a code gap. |
| R-6 | **Cleanup blocking-thread shape** | **Implemented:** the cleanup fan-out is 64. A local 180 s soak peaks at **296/512 threads** versus 430/512 at 128; the 100k delete arm still measures **2,456 obj/s** (within the 2,398-2,494 range at 128). CI later flagged a 134→160 mean shift at only 168/512 peak: tokio's blocking pool warms lazily, so the mean-shift gate was the wrong shape. The thread gate is now a **last-third plateau** (last-third minimum vs middle-third maximum, +16 threshold) with the 512 ceiling unchanged; a local 180 s run is 141→146 threads with a **0 delta** and passes. |
| R-7 | **WAL checkpoint starvation under sustained mixed load** | **Implemented:** the checkpoint's zero-timeout TRUNCATE lost every race against the read pool, so the log only truncated after load stopped. A 100 ms bounded wait lets a normal read finish; `CAIRN_WAL_BACKPRESSURE_BYTES` (default 256 MiB, resume at 25%) is the hard gate when a reader stays pinned. A 120 s soak with the gate forced to 16 MiB engaged **37 times**, each drained in 30-100 ms, with 0 errors and 0 5xx; WAL peaked at **22.3 MiB** (in-flight overshoot) and writers resumed. At the default the cap is ~256 MiB, below the 512 MiB backstop. Do not raise the ceiling. |
| R-8 | **Unwritable logs abort the server** | A two-node soak on a full 512 MB volume returned correct 507s but the source died with SIGABRT. Root cause: `tracing-subscriber`'s default internal-error path reports a failed writer with `eprintln!`; when stdout/stderr are the failed log target, that fallback panics, and `panic = "abort"` turns it into SIGABRT. **Fixed:** the subscriber now drops internal write errors (`log_internal_errors(false)`) in both text and JSON modes. A regression test starts `serve` with both streams on `/dev/full`, probes `/healthz`, and requires a clean SIGTERM exit; the 512 MB two-node reproduction now exits both nodes 0 with no abort. Logging can never stop the server. |

## 8. Decisions the owner must make

Decided by the owner on 2026-11-08: RustFS 1.0.4 is the published comparator, no in-process rate
limiter will be added, and the third-party review is the automated open-source pentest recorded in
[`security-pentest-2026-11.md`](security-pentest-2026-11.md) (not a human certification).

1. **Release tag:** authorize the CalVer 1.0 tag and publication on the green commit.
2. **v44 migration policy:** accept the documented 3× free-space rule and maintenance window; keep
   the atomic `SQLITE_FULL` rollback as the authoritative backstop.
3. **id-index refactor:** stop; the 1.0.4 comparator makes it unnecessary. Revisit only if a
   PLP-device paired benchmark shows the indexed `id` is the remaining delete cap.
4. **Durability exception:** not proposed. The unversioned row remains as-configured; no ACK is moved
   before the durable commit.

## 9. Remaining sequence

1. **Owner decision:** authorize the CalVer tag on the green commit. The comparator, rate-limiting,
   audit, migration-policy and id-index decisions are made.
2. **P0-4:** cut the CalVer tag on the green commit, publish the signed bundle, and attach the
   migration/space/rollback notes. The post-v44 2-hour and 24-hour gates are green.
3. **Post-1.0 hardening:** add the locked-object file-loss rebuild fixture (R-1) and run the
   production-shaped 100M-row drill (R-5) on a real copy. Neither changes the 1.0 support statement;
   they are evidence depth, not code gaps.

The engineering work is complete when the checklist in section 2 is true for the tagged commit, not
when the code merely passes the current CI.
