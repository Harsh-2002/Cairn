# Cairn 1.0 completion plan (2026-11-08)

Status: working plan. Cairn is declared **1.0 (2026-11-07)** in `support.md`; **no 1.0 release tag
has been cut** (latest published tag is `v2026.09.13`). This document lists what is already proven,
what remains before "fully complete", and which items cross a `CONTRACT.md` ceiling and therefore
need an explicit human decision.

## 1. What is proven today

- **Durability.** The metadata transaction is the ACK point; object files and sidecars are the
  durable authority; protocol 3 rebuilds the index from object files at startup. The 24-hour soak
  completed 1,697,128 PUTs with 0 errors, 0 replication mismatches and 137,552 verified reads; the
  fixed 2-hour run held anonymous RSS at 155.6 → 153.5 MiB (−1.3%).
- **Crash/recovery.** CI runs the F-4 crash consistency and the multi-point blob-commit crash
  harness, backup/restore/offline recovery, scrub, Object Lock/WORM, chunked/adversarial limits,
  replication soak/chaos and a mixed-feature leak soak. The mixed-feature thread-shape gate flaked
  once on the v44 head (+35 threads, +16.7%) and passed on a full rerun; R-6 keeps it honest.
- **Security baseline.** No open GitHub code-scanning, Dependabot or secret-scanning alerts at the
  2026-09-25 closure; `cargo audit` and both npm audit policies are in CI; the audit register has no
  unresolved exploitable finding. Known accepted limits are the authentication-path rate limit
  (deploy behind a proxy), OpenRC units, and a residual risk limited to replication ciphertext
  written by pre-fix binaries.
- **Performance.** Against **RustFS 1.0.4**, every paired row is at or above parity: PUT 4 KiB
  1.73x, PUT 1 MiB 1.07x (parity), GET 4 KiB 1.15x, GET 1 MiB 1.64x, HEAD 1.18x, LIST 5.13x,
  Mixed 2.04x, multipart part GET 2.71x, multipart upload 1.08x (parity), bulk unversioned DELETE
  19.95x, single-key unversioned DELETE 16.53x, and versioned DELETE **32.49x** (equal durability).
  RustFS 1.0.2+ journals deletes under strict mode; the 1.0.0 delete rows are historical. The
  delete code path also improved 839.8 -> **1,447.3 obj/s (+72.3%)** in this campaign (2,400+ on the
  quieter 1.0.4 session) and LIST improved to **171,764 obj/s**; with the device flush cost removed
  it reaches **5,680 obj/s** (tmpfs diagnostic).

## 2. What "fully complete" means

A 1.0 is complete when all of the following hold on the release commit:

1. `main` is green on the full gate and on every release-blocking CI job.
2. A release tag and artifacts exist, produced by the release workflow with provenance and signed
   checksums, and the installer verifies them.
3. The supported upgrade path (`v2026.09.13` → current schema) is exercised in CI, including the
   v43/v44 rebuild, Object Lock/retention preservation, snapshot rollback and an old-binary refusal.
4. The release notes state migration time/space and the rollback procedure for the table rebuild.
5. The published scoreboard names the comparator version and pairs only comparable rows.
6. No open high/medium security finding; accepted limits are stated in `support.md`.
7. The 1.0 support statement, `Cargo.toml`/version identity, upgrade guide and README agree.

## 5. Reliability and operability (P1)

| # | Item | Acceptance |
|---|---|---|
| R-1 | **v44 startup rebuild** | Prove a full index rebuild from object files/sidecars on a v44 store restores the clustered rows, listing, `?partNumber`, BLAKE3 baselines and Object Lock exactly. Add to the crash/rebuild harness. |
| R-2 | **Backup/restore v44** | The CI backup/restore e2e already runs on `main`; assert explicitly that a v44 snapshot restores to a v44 store and to the previous release's snapshot path, with lock rows intact. |
| R-3 | **Migration observability** | Log migration name/version, elapsed seconds, WAL growth and free space at startup; expose the last migration duration in `/metrics` or the startup summary. This turns a 110-minute 100M-row upgrade into an observable event. |
| R-4 | **libSQL scope** | Document that the default SQLite backend is clustered at v44 while libSQL/Turso stay at v42 with the rowid layout; no cross-backend DB move is supported. Ensure support/benchmark docs do not imply otherwise. |
| R-5 | **Operational drills** | Re-run upgrade/rollback, disaster recovery and restore on a copy of production-shaped data once after the v44 release; retain the evidence under `docs/performance-evidence/` or the stability record. |
| R-6 | **Cleanup blocking-thread shape** | **Implemented:** the cleanup fan-out is 64. A local 180 s soak peaks at **296/512 threads** versus 430/512 at 128; the 100k delete arm still measures **2,456 obj/s** (within the 2,398-2,494 range at 128). CI later flagged a 134→160 mean shift at only 168/512 peak: tokio's blocking pool warms lazily, so the mean-shift gate was the wrong shape. The thread gate is now a **last-third plateau** (last-third minimum vs middle-third maximum, +16 threshold) with the 512 ceiling unchanged; a local 180 s run is 141→146 threads with a **0 delta** and passes. |
| R-7 | **WAL checkpoint starvation under sustained mixed load** | **Implemented:** the checkpoint's zero-timeout TRUNCATE lost every race against the read pool, so the log only truncated after load stopped. A 100 ms bounded wait lets a normal read finish; `CAIRN_WAL_BACKPRESSURE_BYTES` (default 256 MiB, resume at 25%) is the hard gate when a reader stays pinned. A 120 s soak with the gate forced to 16 MiB engaged **37 times**, each drained in 30-100 ms, with 0 errors and 0 5xx; WAL peaked at **22.3 MiB** (in-flight overshoot) and writers resumed. At the default the cap is ~256 MiB, below the 512 MiB backstop. Do not raise the ceiling. |

## 8. Decisions the owner must make

1. **Release tag:** authorize the CalVer 1.0 tag and publication on the green commit.
2. **Comparator:** accept the 1.0.4 sweep as the published comparator (recommended), or keep the
   pinned 1.0.0 rows with an explicit version label.
3. **Rate limiting:** keep as an accepted deployment limit, or fund it as a product feature.
4. **Third-party audit:** required for the 1.0 claim, or documented as not performed.
5. **v44 migration policy:** accept the measured space/downtime with a preflight, or gate the upgrade
   behind a documented maintenance window.
6. **id-index refactor:** fund it only if the 1.0.4 delete row still needs it; it is not required for
   correctness.
7. **Durability exception:** not proposed. The unversioned row remains as-configured; no ACK is moved
   before the durable commit.

## 9. Suggested sequence

1. **Week 1:** P0-1 (1.0.4 sweep), P0-2 (drill in CI), P0-3 (space/preflight), P0-6 (docs).
2. **Week 2:** P0-4 (release), P0-5 (2 h soak), R-1/R-2 (rebuild/restore v44), S-5 (token note).
3. **Week 3:** security decisions (S-1/S-2/S-3), R-3 (observability), P-2 decision, publish the
   final scoreboard and release notes.

The work is complete when the checklist in section 2 is true for the tagged commit, not when the
code merely passes the current CI.
