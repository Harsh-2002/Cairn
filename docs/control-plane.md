# Control plane: management API, web console, CLI

> Part of the Cairn reference docs. The section numbers below are stable identifiers used throughout the code and docs; see the index in [`CLAUDE.md`](./CLAUDE.md) and [`../CLAUDE.md`](../CLAUDE.md).

## 22. Management API

### 22.1 Role and shape

The management API is the control surface for operating Cairn, distinct from the S3 data surface. It is JSON over HTTP, versioned in its path, gated to administrators, and it is the single API that both the embedded web console and the command-line interface consume, so that whatever can be done in a browser can be done from a terminal and the two never drift. It is not on the object hot path, so it favours clear, stable, well-documented request and response shapes over raw throughput, and it returns errors in a JSON envelope rather than the S3 XML error document. It is served by the same process but only on the optional control listener. That listener has a closed route matrix: `/api/v1` plus concrete embedded-console assets, with no S3 or public-share fallback. Conversely, the data listener rejects the management namespace. `CAIRN_WEB_ADDR=off` removes the control socket entirely.

### 22.2 Endpoints

The API exposes an overview of the store, returning the bucket and object counts, the logical and physical storage totals and thus the achieved compression ratio, and summary replication health. It exposes listing and creating buckets, and a per-bucket detail that returns the bucket's size in logical and physical bytes, its object and version counts, its versioning and ownership state, and each of its configuration aspects, namely its policy, ACL, CORS, lifecycle, replication, tag set, and public-access-block settings, with operations to read and update each aspect so the web console can present and edit them; the same configuration is settable through the S3 subresource operations, and the management API is a convenience over the same stored state. It exposes a force-delete of a bucket that empties it by paging through its contents rather than loading it, for the common operator need to remove a populated bucket, and the same bounded-paging mechanism backs a recursive prefix (folder) delete that permanently removes every object and version beneath a key prefix in one operation, reporting the count removed and signalling with a continuation flag when a very large folder needs the call repeated. These administrator operations are not an Object Lock bypass: the metadata writer evaluates the current retention/legal-hold state atomically with each deletion. A force-delete that encounters protected versions leaves their rows and blobs in place and returns `409`; if unlocked versions were removed before that result, a `DeleteBucketContents` activity entry records the partial destructive write. Recursive deletion continues forward to later unlocked versions and returns a bounded failure list whose entries each carry the exact protected key and version id, with `more=true` while protected or unreported rows remain. Clients de-duplicate failures by that stable pair and stop automatic retry when a pass deletes zero rows. Object-Lock bucket creation likewise commits the bucket, Enabled versioning, and immutable enabled configuration in one writer mutation. It exposes a paged object listing for the data browser, and the minting of Cairn signed public-read (share) URLs for sharing or testing. It exposes user management, namely creating, listing, updating, and deactivating users and rotating their credentials, and the minting of **STS-style temporary session credentials** (`POST /credentials/temporary`) bounded to a 15-minute-to-12-hour lifetime. Its required inline policy is a requested permissions boundary, not a replacement for the administrator's restrictions: the stored session policy uses that boundary's Allows and retains every explicit Deny from the parent identity policy. The endpoint returns the temporary access key, secret, and opaque session token exactly once (Section 14.6). It exposes the activity and audit log with a bounded result limit, and a stored time-series of API request metrics for the usage-analytics view, queryable over a selectable range and downsampled server-side so a chart stays light regardless of traffic (Section 26.5). It exposes replication operations: listing failed replication entries and retrying them, viewing per-bucket replication status, resyncing (backfilling existing objects into replication) through `POST /buckets/{name}/replication/resync` (with `force`/`only_encrypted` query params), and managing the replication targets through the replication-target endpoints. It exposes a bucket's **event-notification (webhook) configuration** — getting, replacing, and clearing the list of webhook endpoints (each an id, URL, event selectors, optional prefix/suffix filter, and optional HMAC secret) — at `GET`/`PUT`/`DELETE /buckets/{name}/notifications`; the get response reduces each endpoint's secret to a presence flag and never echoes the value, and the put validates every endpoint (non-empty unique id, `http(s)` URL, at least one event selector) before sealing a submitted HMAC key under the active master key and storing only its authenticated envelope. Omitting a write-only key preserves the existing value for that endpoint id; an empty string explicitly clears it. This is the only way to configure notifications, since the S3 `?notification` subresource targets SNS/SQS ARNs Cairn does not implement (Section 20.6). And it exposes the non-secret portions of the running configuration and the health and readiness state. Every mutating endpoint records an audit entry.

Import-job history at `GET /imports` is a bounded management listing: `limit` is strictly
`1..1000` (default 1000), `cursor` is the opaque `next_cursor` from the preceding response, and a
null `next_cursor` marks the final page. Ordering is stable newest-first across equal timestamps.
The source secret is excluded at the metadata projection, not merely hidden during JSON encoding.

Persistent shares use a secret-once contract. `POST /buckets/{name}/objects/shares` returns the
stable non-secret `id`, raw bearer `token`, absolute data-origin `url`, and expiry exactly once.
`GET /buckets/{name}/objects/shares[?key=...]` and
`GET /buckets/{name}/objects/shares/{id}` return only the id and non-secret share metadata; they
never return the token, its lookup hash, or a URL from which the bearer could be reconstructed.
`DELETE /buckets/{name}/objects/shares/{id}` revokes by stable id. The CLI and console follow the
same contract: existing-share lists can inspect/revoke but cannot recover or copy an old link.

### 22.3 Authentication and authorization of the control plane

Only a persistent-share **mint** response carries its absolute data-origin URL; later management
responses are capability-free. For raw console S3 operations, the presign endpoint mints or reuses a durable bucket-scoped temporary session, keeps its sealed signing secret server-side, and returns an exact SigV4 URL plus only the session's public key id and opaque token for reuse by the tab. The stored session policy combines that bucket boundary with every explicit Deny in the administrator's identity policy and aborts minting if the parent policy cannot be read or parsed. This flow never opens or exports the administrator's long-lived SigV4 secret.

The management API authenticates with the same credential mechanisms as the rest of the system, with the Bearer scheme being the natural fit for the CLI and any non-browser client, and it requires the administrator role for all operations, refusing members and anonymous requests. The web console signs in once at `POST /session`, where the server validates the administrator credential and returns it as an **httpOnly, `Secure`, `SameSite=Strict` session cookie**; the browser then attaches that cookie automatically to every same-origin call, so the credential is never held in JavaScript-readable storage (closing the cross-site-scripting exfiltration surface a stored token would present). The cookie is honoured **only on the web-console listener** — the S3 data plane on the other port ignores it, even though cookies are not port-isolated — and `SameSite=Strict` keeps it off every cross-site request, which is the cross-site-request-forgery defence. `GET /session` reports the current identity, so the application chooses the console or the login screen without ever reading the cookie, and `DELETE /session` signs out by expiring it. Because the control plane can read and change everything, it is held to the same wire-security expectations as the rest of the system: it is served over TLS, whether terminated by Cairn or by a proxy, and credentials never traverse an untrusted hop in clear. Native TLS is authoritative. When a reverse proxy terminates TLS, its immediate peer IP/network must be present in `CAIRN_TRUSTED_PROXIES` and it must overwrite `Forwarded` with a validated `for=…;proto=https` chain or overwrite `X-Forwarded-Proto` with the single value `https`; only then does Cairn mark the cookie `Secure`. Headers from an untrusted peer, an unparseable chain, duplicate/conflicting protocol assertions, and unverifiable multi-valued `X-Forwarded-Proto` are ignored in the privilege-increasing direction. A direct loopback plaintext listener deliberately keeps a non-`Secure` cookie for local development.

## 23. Embedded web console

### 23.1 What it is and how it ships

The management web console is a single-page application built with the React framework and its standard build toolchain, and it is compiled into the Cairn binary at build time so that a Cairn deployment is one binary that already contains its own management interface, with no separate web console service to deploy, host, or version-match. The built static assets, the markup, the script bundles, and the styles produced by the web console build are embedded into the binary through a compile-time asset-embedding mechanism that bakes the asset directory into the executable, and the server serves them from memory. This is the operator's stated requirement that the web console be installed and compiled into the binary itself and that management be possible through either the web console or the CLI, and it is satisfied by making the web console a build-time artifact of the same binary.

### 23.2 The build pipeline

Building Cairn with its web console is a two-stage process that the workspace orchestrates so that a normal release build produces a web console-containing binary. The first stage runs the Node toolchain to produce the optimised static asset bundle from the web console source. The second stage compiles the Rust binary with the asset-embedding step pulling that bundle into the executable. The orchestration caches the asset build so that Rust-only changes do not rebuild the web console and web console-only changes do not needlessly recompile unrelated Rust, which keeps the developer loop fast, and a build feature allows producing a binary without the embedded web console for cases that want a smaller artifact or a faster build, in which case the web console routes are simply absent. The result is reproducible: the same sources produce the same binary with the same embedded web console.

### 23.3 Serving and behaviour

The server serves the embedded single-page application under a management web console path, returning the application shell for client-side routes so that the framework's routing works on reload, and serving the script and style assets with appropriate caching headers since they are content-hashed by the build. The application is a client of the management API: it authenticates the operator, then renders the store overview with the storage and compression and replication figures, a bucket view for listing and creating buckets and for editing each bucket's versioning, quota, default encryption, compression, bucket policy, and replication settings while showing its CORS, lifecycle, tagging, and public-access-block configuration read-only, a data browser for paging through objects and for uploading, downloading, deleting, and generating share URLs, a user-management view, an activity and audit view, and a replication-status view that surfaces lag and failures and offers retry. The navigation sidebar lets the operator expand the buckets entry into an inline accordion that lists the buckets and deep-links straight into each one's browser, so a named bucket is one click away without first loading the list. The data browser previews an object **in place**: selecting one opens a viewer that renders images, video, audio, PDF, Markdown, JSON, delimited data, and text or source directly in the console, with keyboard paging through the surrounding folder, so inspecting stored data no longer means downloading it. Rendering is confined to mechanisms that cannot execute the object's bytes as active content in the console's origin (Section 27): media through inert element contexts, PDF through a frame the server is forced to label `application/pdf` — which, with the `nosniff` the object surface always sends, routes an HTML-bodied object to the PDF viewer rather than the HTML parser — and textual types fetched and rendered as inert text, range-capped so a large object cannot be pulled into the page. Types with no safe or useful rendering fall back to an explicit download. The browser also deletes a whole folder by invoking the recursive prefix delete behind a confirmation that states the action is permanent. A dedicated metrics view charts API request volume over time with a one-day, one-week, two-week, or one-month range, alongside a breakdown by operation and the most active buckets, drawn from the request-metrics subsystem (Section 26.5). A Tags view lists every object tag in use across the buckets with its object count and drills into the objects carrying a chosen tag, and the object browser can filter its listing to a single tag (Section 17.2). The web console changes nothing that the API does not expose, so it carries no privileged logic of its own and remains a thin presentation over the control plane.

### 23.4 Security posture of the web console

Because the web console is served by the same process and talks to the same admin-gated API, its security reduces to the API's: it requires an administrator session, it is served over TLS, and it is subject to the same audit logging for the actions it triggers. The web console authenticates with an **httpOnly session cookie** set at sign-in rather than a JavaScript-stored token, so a cross-site-scripting flaw cannot read the credential out of the page; `SameSite=Strict` keeps the cookie off cross-site requests, which is its cross-site-request-forgery defence, and serving the application from the same origin as the API lets it reach the management path without cross-origin configuration. The web console exposes no secret material beyond what an administrator is entitled to see, with credentials shown once at creation and only hashes and ciphertext retained thereafter.

Raw S3 calls never use that cookie-bearing origin. The browser asks the management API for a short-lived exact data-origin URL, performs the request with ambient credentials omitted, and retains only the reusable non-signing session handle in memory. A signed console-origin marker grants CORS metadata only to the exact origin/request; it is not authorization, and the SigV4 session is still validated normally. Object bytes and public shares therefore remain on a distinct data origin, where stored HTML or SVG cannot execute with the management origin's cookie. A deployment proxy must retain this origin separation.

## 24. Command-line interface

### 24.1 Role

The command-line interface is the terminal-first way to operate Cairn and is a first-class peer of the web console, not an afterthought. It serves two distinct purposes. For remote administration it is a client of the management API, so that an operator can do from a terminal or a script everything the web console offers, which suits automation and remote management. Remote commands take independent endpoints: `--endpoint` / `CAIRN_ENDPOINT` selects the control API, while `--s3-endpoint` / `CAIRN_S3_ENDPOINT` selects the data listener for direct object commands. For node-local operations that must run on the host and that operate directly on the data directory and the database, it provides commands that do not go through the API, because some operations are inherently local or must run when the server is not serving. Shipping both as subcommands of the same binary keeps the deployment a single artifact.

### 24.2 Remote administration commands

As an API client the CLI offers commands mirroring the management API: creating, listing, and removing buckets and force-emptying them; reading any bucket configuration aspect through `config get`, and writing the bucket policy through `config set` taking the document from a file so it can live in version control; managing users and rotating credentials; browsing and listing objects; uploading, downloading, and removing objects; and configuring replication targets, and viewing, retrying, and resyncing (backfilling existing objects into) replication — `replication resync <bucket> [--force] [--all-versions]` and `replication target add`. It is configured by flags or the corresponding `CAIRN_*` environment variables giving the endpoint, access key, and secret key, and it can emit either human-readable output for interactive use or structured output for scripting, so it composes into automation.

### 24.3 Node-local commands

The local commands run on the host against the data directory and database directly. They include the bootstrap command that ensures the single root administrator exists (the same identity `serve` seeds from `CAIRN_ROOT_ACCESS_KEY` / `CAIRN_ROOT_SECRET_KEY`) and prints its credentials — idempotent, so it never produces a second default admin; an integrity command that runs reconciliation on demand and, in its repair mode, resolves divergences such as rows whose blobs are missing, which is the recovery tool referenced by the durability and backup sections. Repair uses the same writer-level Object Lock gate as every API path: a retained or legally-held missing-blob row is preserved, counted as `protected_unresolved`, and makes the command fail so an operator must resolve the damaged protected version explicitly rather than silently erase WORM metadata. The local set also includes a backup command that performs the consistent snapshot procedure of Section 31 and its counterpart `restore <DIR>` command that places a snapshot into the data directory and runs reconciliation (ARCH 31.4); a `replication audit --before <ts> [--bucket] [--json] [--verify]` command that reads the durable per-version `replication_status` ledger directly; configuration validation that checks a configuration without starting the server; and the database migration that the server also runs at startup, exposed for operators who prefer to migrate explicitly. These commands are how an operator bootstraps, verifies, backs up, and repairs a deployment from the host shell, complementing the remote administration that the API-client commands provide.
